## 1. Что это за проект

SportBuddy78 — российский сервис для знакомств и поиска спортивных партнёров в Санкт-Петербурге:
совместные тренировки, мэтчи, чаты, лента, официальные мероприятия, Premium.

Доставляется как **PWA** (устанавливается на телефон из браузера) и **Android APK** (Capacitor).

Статус: **production beta**, идёт контролируемое тестирование на реальных пользователях.
В боевой базе на 3 октября 2026 — 20 реальных профилей.

## 2. Стек и архитектура

| Слой | Технологии |
|---|---|
| Фронтенд | React 19, TypeScript 5.9 (strict), Vite 7, Tailwind CSS 4, Framer Motion, react-virtuoso |
| Карты | Leaflet + OpenStreetMap (без API-ключей) |
| Мобильная обёртка | Capacitor 8 (Android) |
| API | Node 22, Express 5 (`server.js` + `server/app.js`), 12 маршрутов |
| База и auth | Firebase Firestore + Firebase Auth (Admin SDK на сервере) |
| Медиа | Cloudinary (unsigned upload, фото и видео) |
| Платежи | ЮKassa (API + webhook) |
| Почта | Яндекс.Почта через nodemailer (OTP и сброс пароля) |
| Рядом | self-hosted Supabase в Docker — **не** primary datastore, код на него не переключён |

**Ключевой принцип: клиент не источник истины для критичных данных.**

```
Firebase UID → Server API (Express) → Firebase Admin SDK → Firestore
```

Клиентские записи в `users`, `trainings`, `feed`, `payments`, `chats`, `friendships`
запрещены правилами Firestore (`firestore.rules`). Любая значимая мутация идёт через
`/api/sportbuddy-mutation` или профильный эндпоинт, где сервер проверяет ID-токен.

## 3. Инфраструктура и деплой

**VPS:** российский (REG.RU), Ubuntu 24.04 LTS, 4 vCPU / 4 ГБ RAM / 80 ГБ, Nginx + PM2 + Docker.
Адрес, ключи и SSH-доступ хранятся у владельца и в этот документ не попадают (репозиторий публичный).

Nginx отдаёт статику из `/opt/sportbuddy-current/dist` и проксирует `/api/` на `127.0.0.1:3001`,
где слушает `server.js` под PM2 (процесс `sportbuddy-api`).

### 3.1 Релизный контур (главное, чего нет в старых паспортах)

```
/opt/sportbuddy-source        чекаут репозитория (источник релизов)
/opt/sportbuddy-releases/<sha>  каталоги релизов, по одному на коммит
/opt/sportbuddy-current       symlink → активный релиз   ← его и отдаёт nginx
/opt/sportbuddy-deploy        состояние деплоя: pm2-снимки, previous-release, lock-файлы
/opt/sportbuddy-api           LEGACY-чекаут, оставлен как цель отката; приложение оттуда НЕ работает
```

Скрипты (`ops/` в репозитории):

```bash
# 1. Подготовить релиз из проверенного коммита (живое приложение не затрагивается)
#    внутри: git archive → npm ci --include=dev → npm audit --audit-level=high → npm test → npm run build
bash ops/prepare-release.sh /opt/sportbuddy-source <ПОЛНЫЙ_SHA_40> /opt/sportbuddy-api/.env

# 2. Активировать (атомарная подмена symlink + пересоздание PM2 с проверкой путей и health)
bash ops/activate-release.sh /opt/sportbuddy-releases/<ПОЛНЫЙ_SHA_40>

# 3. Проверить снаружи
curl -fsS https://sportbuddy78.pro/api/health      # должно вернуть release: <SHA>
curl -fsS -o /dev/null https://sportbuddy78.pro/
```

Откат — тем же `activate-release.sh` на каталог из `/opt/sportbuddy-deploy/previous-release`.
При провале активации скрипт восстанавливает и symlink, и регистрацию PM2 автоматически.
Полная процедура с бэкапом и приёмочными проверками — `ops/RUNBOOK.md`.

**Важно:** `prepare-release.sh` содержит гейт `npm audit --audit-level=high` и запускается с `set -e`.
Любая уязвимость уровня high **блокирует релиз** — при правках зависимостей это надо проверять заранее.

**Важно:** деплой не «пуллом в живом каталоге». Не делать `git pull` в `/opt/sportbuddy-api`:
это legacy-копия, и её состояние — точка отката.

## 4. Ветки: где находится правда

Это место, где ошибались оба старых паспорта («Основная ветка: main»).

| Ветка | Состояние |
|---|---|
| `feat/feed-and-onboarding` | **прод** (`8a337204`): правки ленты/эфира, окно возможностей, чистый audit |
| `fix/vps-vk-identity` | предыдущий прод (`e2bf4ca9`): VK-идентичность, уведомления, геолокация |
| `main` | **отстаёт на 20 коммитов.** Свежий клон по умолчанию получает августовский код (`af86aa31`) |

Правило: **релиз идёт с feature-ветки, а не с `main`.** Пока `main` не выровнен, он не является
источником истины, и любой, кто клонирует репозиторий «как есть», получит нерабочую картину.

Независимый стек из 14 коммитов (`fix/server-authoritative-training-membership` → …
→ `chore/repo-hygiene`), плюс `test/auth-regression-gate` — **в прод не влиты**. По содержанию
их темы (VK-linking, восстановление профиля, синхронизация верификации, серверная модель участия)
уже реализованы в прод-линии собственными коммитами. Уникально там только одно:
`.github/workflows/quality-gate.yml` (проверки сборки, синтаксиса сервера и безопасности) —
**в прод-ветке CI отсутствует**.

## 5. Данные: Firestore

Основные коллекции: `users`, `usersPrivate`, `trainings`, `feed`, `chats`, `friendRequests`,
`friendships`, `checkins`, `ratings`, `payments`, `workoutCredits`, `goals`, `promoCodes`,
`events`, `vkIdentities`, `adminSessions`, `notificationInboxes`.

Принципы:

- `users/{uid}` создаётся и инициализируется **сервером** (`bootstrapProfile`), не клиентом.
- Чувствительные поля (`email`, `phone`, `birthDate`, `deviceId`) живут в `usersPrivate/{uid}`
  и читаются только самим пользователем.
- Прогресс, Premium, верификация, участие в тренировках, друзья, мэтчи — запрещены к правке с клиента.

### 5.1 Демонстрационные данные (устранено 3 октября 2026)

Демо-режим когда-то записал в **боевую** базу 18 служебных документов: 7 профилей
(`user-anna`, `user-daria`, `user-ekatery`, `user-elena`, `user-maria`, `user-veronika`, `user-me-1`),
3 поста с датами-строками («2 часа назад», «Вчера») и 8 тренировок `tr-101…tr-108`.

Они удалены скриптом `scripts/cleanup-demo-data.mjs` (по умолчанию — предпросмотр,
`--apply` — удаление, `--backup <файл>` — копия удаляемого). Копия на VPS: `/root/demo-cleanup-backup.json`.

При удалении затронуты следы реальных людей на фейковом контенте: два лайка и один комментарий
к фейковому посту `post-1`, одна запись реального аккаунта на фейковую тренировку `tr-103`.

Защита от повторения: демо-набор включается только при `DEV` + `VITE_ENABLE_SAMPLE_DATA=true`
(`src/lib/sampleData.ts`), служебные id отфильтровываются на чтении, версия offline-кэша поднята
до `sportbuddy_offline_cache_v4`.

## 6. Аутентификация и идентичность

- Основная идентичность — **Firebase UID**.
- Способы входа: **VK ID** (основной) и email/пароль.
- VK: сервер проверяет access token, ведёт маппинг `vkIdentities/{vkId} → uid`
  (`server/vk-identity.js`) и выдаёт custom token.
  Принципиально: **никакого слияния и удаления аккаунтов при входе**; неоднозначные legacy-идентичности
  отклоняются, а не «сходятся» в один профиль; email от VK опционален и не создаётся искусственно.
- Анонимный вход в проекте **отключён** (`ADMIN_ONLY_OPERATION`).
- Устаревшие `acc_vk_*` и идентичность из localStorage — не источник истины.

## 7. Premium, бета и лимиты

Политика одна на клиент и сервер — `shared/access-policy.js`:

- бета активна с 30.09.2026 до **01.01.2027** (московская полночь), в этот период Premium открыт всем;
- Premium выдаётся сервером при создании профиля (`premiumUntil`), клиент только читает;
- **SportBuddy BOX** заблокирован до 01.01.2027, промокоды при этом копятся;
- **бесплатный тариф: 5 взаимных мэтчей за 7 дней**, Premium снимает лимит.

## 8. Платежи

```
Пользователь → ЮKassa → webhook /api/payment-webhook → проверка на сервере
            → Firestore-транзакция → premiumUntil
```

Premium никогда не выдаётся по сообщению клиента. Обработка webhook идемпотентна.
**Платежи после переезда на VPS не тестировались на живых деньгах** — нужен тестовый платёж.

## 9. Лента и видеозапись

Исправлено 3 октября 2026:

- порядок в ленте задаёт **дата публикации**, а не строковый `id` (раньше свежий пост уезжал вниз);
- подписи дат человекочитаемые («только что», «12 мин назад», «вчера», дата);
- демо-посты не подставляются пользователю;
- «Прямой эфир» заменён на честную **видеозапись**: `MediaRecorder` пишет клип, он публикуется
  в ленту через обычный диалог подписи. Выдуманных зрителей (`Math.random`) больше нет.

Публикации требуют подтверждения профиля; на бета-периоде Premium доступен всем.

## 10. Медиа и уведомления

- Всё медиа идёт через Cloudinary (`src/services/cloudinary.ts`): фото ≤ 10 МБ, видео ≤ 100 МБ,
  трансформации `f_auto,q_auto`, прогресс загрузки через XHR.
- Уведомления: `notificationInboxes` + FCM web push. Для нативного Android push нужна
  отдельная интеграция — это не тот же механизм, что web push.
- Service worker (`public/sw.js`) — network-first, кэширует только статику и медиа,
  API/Firestore не перехватывает.

## 13. Открытые задачи

1. **Приватность геолокации.** Визуальное смещение маркера на карте не скрывает точные
   координаты в данных профиля. Нужно решение до широкого запуска: округление координат
   или отдельное «публичное» поле.
2. **Выровнять `main`** на актуальный коммит, иначе дефолтный клон остаётся устаревшим.
3. **Правила Firestore в проде** — сверить с версией из репозитория.
4. **CI** — перенести `quality-gate` из невлитой ветки или написать заново (тесты уже есть).
5. **Техдолг:** `src/App.tsx` ≈ 3800 строк; подписка на коллекцию `feed` перезагружает
   все данные целиком при любом изменении.
6. **Уборка веток** — 6 устаревших веток-дубликатов удалить или пометить как архив.

## 14. Почему старые паспорта расходятся с реальностью

| Утверждение в старых паспортах | Как на самом деле |
|---|---|
| «Основная ветка: main» | прод идёт с feature-ветки; `main` отстаёт на 20 коммитов |
| деплой через `/opt/sportbuddy-api/deploy.sh` | такого файла нет; деплой — через `ops/*.sh` и релизные каталоги |
| nginx отдаёт `/opt/sportbuddy-api/dist` | отдаёт `/opt/sportbuddy-current/dist` |
| релиз `66c623cd`, 72 теста | прод `8a337204`, тестов 80 |
| «0 уязвимостей» | на коммите `e2bf4ca9` аудит падал (4 high); исправлено 3 октября |
| «Node.js 20» | Node 22.23.3, npm 10.9.9, pm2 7.0.4 |
| Supabase как часть архитектуры | развёрнут рядом, в коде не используется |

Причина расхождений простая: паспорта писались по состоянию на определённую дату,
а работа продолжалась в ветках и на сервере. Поэтому единственный надёжный источник —
сам репозиторий (в правильной ветке) и релизные каталоги на VPS.
