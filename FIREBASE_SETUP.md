# Firebase — настройка проекта `sportbuddy-spb`

Приложение подключено к вашему проекту. Ключи прописаны в
`src/lib/firebase.ts` и могут переопределяться через `.env.local`.

---

## ⚠️ Главное про безопасность

**Web API-ключ Firebase не является секретом.** Он лишь указывает SDK, к какому
проекту обращаться, и всегда виден в собранном JS-бандле любого веб- или
мобильного приложения. Google это подтверждает официально.

Данные защищают **Firestore Security Rules** — они уже написаны в
`firestore.rules`. Без их публикации база будет открыта всем.

```bash
npm i -g firebase-tools
firebase login
firebase use sportbuddy-spb
firebase deploy --only firestore:rules,firestore:indexes
```

Для админ-панели, верификации и серверного антифрода дополнительно:

```bash
firebase deploy --only functions
```

Cloud Functions также обеспечивают верификацию и антифрод:
- `verifyMyProfile` выставляет `isVerified` только после серверной проверки
  личного аватара и минимум одного фото в портфолио;
- `cleanupExpiredUnverifiedUsers` запускается каждые 15 минут и удаляет аккаунты,
  не прошедшие верификацию за 24 часа.
- `deleteMyExpiredUnverifiedAccount` выполняет ту же очистку моментально, если
  просроченный пользователь всё же открыл приложение.

> Для планового удаления нужен Firebase Blaze plan / Cloud Scheduler.

Фото профилей, портфолио, ленты и промо-материалы хранятся в **Yandex Object
Storage**. Клиент получает временный signed URL от Vercel-функции
`/api/upload-file`; ключи Yandex остаются только в Vercel Environment
Variables.

Подробная настройка SMTP, одноразовых кодов и Firebase Functions находится в
[`functions/README.md`](functions/README.md).

Дополнительно рекомендую в консоли Google Cloud ограничить API-ключ:
**APIs & Services → Credentials → ключ → Application restrictions**
- Android: package `ru.sportbuddy.mobile` + SHA-1 отпечаток релизного keystore
- Web: домены `sportbuddy-spb.web.app`, `localhost`

## 1. Включите провайдеры входа

Firebase Console → **Authentication → Sign-in method**:

| Провайдер | Зачем |
|---|---|
| **Anonymous** | Обязательно. Даёт `request.auth.uid` каждому устройству, иначе правила заблокируют все записи |
| **Email/Password** | Обязательно. Регистрация и вход по почте |

> Без **Anonymous** приложение продолжит работать, но синхронизация с облаком
> будет отключена (всё останется в локальном кеше).

---

## 2. Создайте базу Firestore

Console → **Firestore Database → Create database**

- Режим: **Production mode**
- Локация: **eur3 (europe-west)** — ближе к РФ, ниже задержки

## 3. Опубликуйте правила и индексы

```bash
firebase deploy --only firestore:rules,firestore:indexes
```

Медиа-файлы не используют Firebase Storage: загрузка выполняется напрямую в
Yandex Object Storage по signed URL. Инструкции — в `YANDEX_STORAGE_SETUP.md`.

Что защищают правила (`firestore.rules`):

| Коллекция | Правило |
|---|---|
| `users` | Читают все авторизованные; редактировать можно только свой профиль. **Поля прогресса заблокированы** от клиента — накрутить тренировки, медали или Premium через консоль браузера нельзя |
| `trainings` | Создаёт любой авторизованный; редактирует только организатор. Остальные меняют лишь `participantIds` и `checkedInUserIds` |
| `events` | Создаёт и удаляет **только** `support@sportbuddy78.ru` |
| `chats` | Строго приватны — доступ только двум участникам |
| `ratings` | Двусторонние оценки 1–5 после завершённой тренировки: организатор → участник и GPS-подтверждённый участник → организатор; отзывы неизменяемы |
| `checkins` | Неизменяемый журнал отметок о прибытии |
| `*` | По умолчанию — полный запрет |

Публикация в `feed` требует одновременно: авторизованный Firebase UID,
Premium-доступ и серверное поле `users/<uid>.isVerified == true`.

> **Важно для production:** агрегаты прогресса (`totalWorkouts`, медали,
> рейтинг, Premium) намеренно заблокированы для прямой записи с клиента.
> Для синхронизации этих полей между устройствами подключите доверенные
> Firebase Cloud Functions / Admin SDK, которые валидируют GPS check-in,
> завершение тренировки и взаимные оценки на сервере. До этого мобильный
> клиент работает в offline-first режиме и хранит подтверждённый прогресс
> локально, не ослабляя Security Rules.

## 4. Первый запуск и чистый старт

При первом запуске аккаунт получает **чистый профиль**: нулевой рейтинг,
нулевые тренировки и медали, Бронзовый уровень, пустые друзья/мэтчи/чаты.

Демо-профили и демонстрационные тренировки **не записываются в Firestore**
и отключены в production. Для локальной визуальной разработки их можно
включить только через `VITE_ENABLE_SAMPLE_DATA=true`.

> Это защищает таблицу лидеров и статистику сообщества от ботов и
> предустановленного прогресса.

### Идентичность Firestore

Документы профилей и объектов пользователя используют **Firebase Auth UID**
как `id`. Локальный `AuthAccount.id` нужен только для интерфейсной сессии и
персонального offline-журнала. Это соответствует `request.auth.uid` в
Security Rules и исключает пересечение профилей на одном устройстве.

## 6. Проверка интеграции

```bash
npm run dev
```

1. Откройте **DevTools → Network → фильтр `firestore`** — должны идти запросы
   к `firestore.googleapis.com`
2. **Console** не должна содержать `permission-denied`
3. В Firebase Console → Firestore появятся коллекции `users`, `trainings`, `feed`
4. Отключите сеть → приложение продолжит работать → включите сеть →
   изменения досинхронизируются автоматически

## Архитектура синхронизации

Приложение построено по принципу **offline-first**:

```
Действие пользователя
   ↓
localStorage (мгновенно)  →  UI обновляется без ожидания сети
   ↓
backgroundWrite() с таймаутом 3.5 с
   ↓
Firestore  ─── нет сети? ──→  очередь syncOfflineQueue()
```

Интерфейс **никогда не ждёт** ответа сервера. Все обращения к Firestore
обёрнуты в `withTimeout()`, поэтому недоступность сети не может подвесить
экран загрузки.

Включена **persistentLocalCache** с поддержкой нескольких вкладок:
Firestore сам хранит данные в IndexedDB и повторяет отложенные записи.
