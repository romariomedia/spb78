# Avatar recovery, photo editor and Stories — 2026-10-04

## Behaviour
- Avatar images in the profile summary, chat views, match dialog and feed retry the original Cloudinary upload if the generated thumbnail fails, then use the local placeholder. This does not recover deleted originals or expired external VK URLs; run the diagnostic below to establish that cause before replacing a user's photo.
- Feed > From gallery opens the photo editor for images; video keeps the existing caption flow. Editor supports original / 1:1 / 4:5 / 9:16 crop, zoom, crop positioning, quarter turns, warm/cool/mono filters, brightness and contrast. It exports a new JPEG, leaves the source untouched, and renders filters with pixel operations for mobile canvas compatibility. Preview and exported image use the same rendering code.
- Stories are for authenticated readers. Publication requires a verified profile and server-authoritative Premium access: open beta until Moscow midnight 2027-01-01, then an unexpired Premium subscription (including redeemed rewards). Read access stays free. UI availability is only a hint; API rechecks eligibility.
- Five publications per owner per Moscow calendar day, including deleted stories. Request IDs prevent duplicate publication after a lost response. Photo input <=2 MiB JPEG, <=6 megapixels; server decodes/re-encodes and strips metadata, outputs at most 1080x1920. Captions <=240 characters. Maximum two simultaneous uploads per Node process; limit 90 API requests per user/minute. Single PM2 instance as in the existing deployment.
- Stories expire on server time exactly 24 hours after publication: listing and image read reject expired records; open viewers hide the photo at expiry. Expiry is not based on Firestore TTL cleanup. Files and metadata are swept every ten minutes (up to 200 expired records per sweep); abandoned files older than 25h are removed. Cleanup errors are logged. Media is delivered via an authenticated POST with Cache-Control:no-store, not a public static directory. Recipients can still save screenshots/copies.
- List pages contain up to 60 stories, with a More button. Only the opened photo is downloaded. No video stories, background autoplay or viewer tracking in this release.

## VPS storage and operation
`SB_STORIES_DIR` defaults to `/opt/sportbuddy-media/stories`, outside release directories. The existing root PM2 user can create it; if running as another user, provision this directory for that user (0700). Never place it under dist or configure a public nginx alias. Include it in backup/restore procedures if stories must survive VPS recovery. Release rollback does not delete media.

Uploads stop with a readable error below 5 GiB of free disk space or at 2000 stored JPEG files. These are guardrails, not a server load benchmark. Editor calculations happen on the user's device; server does bounded image decoding and resize. Firestore stores metadata, quota counters and profile reads. No paid Firebase Functions, Firebase Storage or Cloudinary credentials are added for stories; existing feed/avatar uploads still use Cloudinary.

Traffic estimate (not a measurement): 1000 active stories at 250 KiB each use ~244 MiB of disk; 10,000 photo views at that size deliver ~3.2 GiB with base64 overhead. Actual JPEG sizes and host bandwidth limits matter. The last supplied VPS report had 59 GiB free; obtain current `free -h`, `df -h /opt`, `nproc`, `pm2 status` before predicting large-audience capacity. Firestore's free request allowance is a separate limit. Test after deployment with two accounts; no load test or real mobile-device camera test has been performed here.

Nginx may impose its default 1 MiB body limit before Express sees an upload. Ensure `client_max_body_size 4m;` in the site's existing `/api/` location (or relevant server block). Inspect first; preserve all proxy headers and other routes. Run `nginx -t` before reload. Express already allows 10 MiB.

## Avatar diagnostics and test profile cleanup
From the active release, run `node scripts/profile-maintenance.mjs`. It reads profiles and probes approved media hosts with bounded requests; prints UID, name, avatar/thumbnail HTTP status and candidate flags, never credentials or full photo URLs. A 200 response from the VPS does not prove the user's mobile network can reach the CDN.

`node scripts/profile-maintenance.mjs --archive UID1 UID2` archives only explicitly supplied, empty, unverified profiles named exactly `Новый спортсмен`, older than 24h, with no uploaded avatar or portfolio and no checked business activity. It disables/revokes their Auth account, copies public/private documents to `archivedTestProfiles/{uid}`, then removes the public/private originals. A profile with chats, friends, training membership, payments, checkins, posts or stories is refused. No bulk deletion by display name. Run only after reviewing the report; archive recovery requires restoring those two documents and re-enabling the original Auth account. Existing issued tokens in other endpoints may remain valid until expiry; disabled identities cannot sign in again. No profiles were changed during development.
