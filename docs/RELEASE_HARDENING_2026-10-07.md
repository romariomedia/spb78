# Исправления связности и защиты SportBuddy78

Изменения подготовлены для VPS / Node 22. Публикация приложения и публикация
Firestore Rules — разные операции. Обычная пересборка не обновляет правила базы.

## Что меняется

- Спортивный ID читается даже после удаления основного спорта из профиля.
  При следующем редактировании предлагается выбрать актуальный спорт. История сохраняется.
- Победы считаются по всей подтверждённой истории; карточка выводит последние 50 результатов.
- Изменения ID и отзыв устаревших подтверждений записываются транзакцией.
  Одобрение, отклонение и отмена заявки проверяют актуальное состояние.
- Публичная карточка не кэшируется HTTP-кэшами; QR создаётся локально и скачивается PNG.
- Новые документы подтверждения передаются через авторизованный API и хранятся вне
  каталога сайта на VPS. Скачивание доступно владельцу либо администратору с OTP-сессией.
- JPEG/PNG/WebP преобразуются в JPEG без EXIF; PDF выдаётся как скачиваемый файл.
  SVG/HTML не принимаются. До 4 МБ, 10 загрузок в сутки и 50 МБ на пользователя.
- Лента запрашивает только isHidden=false; правила запрещают прямое чтение скрытых постов.
  Слушатель обновлений использует тот же фильтр. Уже скачанные пользователями копии
  нельзя отозвать задним числом.
- Центр подтверждений фильтрует заявки на сервере до ограничения страницы. Есть загрузка следующих страниц.
- Скрытые/архивные направления не подставляются из статического каталога.
- Ошибка чтения аналитики показывается как ошибка. D7 рассчитан по вчерашнему,
  завершённому дню МСК. Дата первого наблюдения относится к текущему 14-дневному окну.

## Порядок публикации

1. Сохранить резервную копию Firestore и текущих Firestore Rules, конфигурации,
   указателя `/opt/sportbuddy-current`. Не публиковать старый клиент вместе с новыми
   правилами: его запрос всей коллекции ленты будет отклонён.
2. Создать постоянное закрытое хранилище **от имени пользователя процесса PM2**:

   ```bash
   install -d -m 700 /opt/sportbuddy-data/private-evidence
   ```

   Если каталог создаёт root, а PM2 запущен другим пользователем, назначить владельца
   каталога этому пользователю. Не добавлять каталог в nginx `root`/`alias`.
   В рабочий серверный `.env`, который передаётся `prepare-release.sh`, добавить:

   ```dotenv
   SB_PRIVATE_MEDIA_DIR=/opt/sportbuddy-data/private-evidence
   ```

   Это серверная переменная, без префикса VITE. Включить каталог в закрытые резервные
   копии вместе с Firestore: одних документов базы для восстановления файлов недостаточно.
   Без настройки загрузка вернёт 503, остальные разделы приложения продолжат работать.
   Проверить лимит тела запроса nginx для `/api/`: не меньше `8m`, поскольку файл
   до 4 МБ передаётся в JSON как base64. Если установлен больший лимит — оставить его.
   После изменения выполнить `nginx -t`, затем `systemctl reload nginx`.

3. Заранее опубликовать `firestore.indexes.json` (новый индекс заявок: status + updatedAtMs) и дождаться состояния Enabled в Firebase Console:

   ```bash
   npx firebase-tools deploy --only firestore:indexes --project sportbuddy-spb
   ```

   Затем подготовить релиз стандартным `ops/prepare-release.sh` по полному SHA ветки.
   Далее выполнять команды из каталога **подготовленного релиза** с его `.env`:

   ```bash
   node scripts/backfill-feed-visibility.mjs
   node scripts/backfill-feed-visibility.mjs --apply
   ```

   Первый запуск — просмотр количества записей. Второй дополняет старые записи полем
   `isHidden=false`, не изменяя уже заданные решения модератора. Повторный запуск безопасен.
4. Активировать подготовленный релиз штатным `ops/activate-release.sh`.
   Сразу повторить backfill — это захватит посты, созданные старой версией во время подготовки.
   С этого момента новые посты уже содержат `isHidden=false`.
5. Опубликовать `firestore.rules` из **этого релиза** в правильный Firebase-проект.
   Если Firebase CLI уже авторизован:

   ```bash
   npx firebase-tools deploy --only firestore:rules --project sportbuddy-spb
   ```

   Проверить имя проекта по серверной конфигурации перед выполнением. Если CLI ещё не
   авторизован, использовать свою административную учётную запись Firebase.
   Пока правила не опубликованы, скрытые посты остаются читаемыми напрямую.
6. Старые документы Cloudinary проверить и перенести отдельно:

   ```bash
   node scripts/migrate-verification-evidence.mjs
   node scripts/migrate-verification-evidence.mjs --apply
   ```

   Скрипт принимает ссылки только вашего Cloudinary cloud, запрещает перенаправления,
   ограничивает размер. Копия сначала сохраняется в закрытом хранилище, затем ссылка
   в заявке заменяется идентификатором. Ошибки требуют ручной проверки; источники
   больше 4 МБ, чужие cloud и неподдерживаемые форматы не переносятся автоматически.

   **Публичные оригиналы скрипт не удаляет.** После проверки частных копий удалить
   соответствующие оригиналы документов в Cloudinary с инвалидированием CDN.
   Список исходных URL находится в закрытой коллекции `sportEvidenceMigrations`,
   поле `sourceUrl`. Аватары и фотографии ленты не удалять. До удаления оригиналов
   прежние URL могут оставаться доступными. Для подтверждённо удалённых оригиналов
   отметить `publicCopyRemovalRequired=false` в соответствующей записи миграции.
7. Проверить на телефоне после обновления страницы/приложения:
   - обычный пост виден; после скрытия исчезает; прямое чтение скрытой записи запрещено;
   - ID открывается после изменения списка спорта; QR ведёт на публичную карточку;
   - новый документ скачивается владельцем и администратором, недоступен другому аккаунту;
   - решение администратора сохраняется, изменение достижения отзывает подтверждение;
   - скрытое направление не позволяет создать новую встречу;
   - аналитика показывает D7 за завершённый день.

## Откат

Backfill не удаляет данные и совместим со старым кодом. Однако старый клиент не умеет
фильтровать ленту по новым правилам, а старый API не умеет читать закрытые документы.
После включения защиты предпочтителен исправляющий релиз поверх этой версии.
Полный откат правил снова открывает скрытые записи и не должен быть обычным действием.
Не удалять каталог private-evidence при очистке релизов.

## Границы проверки

базой, типы файлов, права владельца, квоты и миграция видимости. Рабочие Firebase Rules,
права каталога PM2 и скачивание из Android требуют проверки после публикации на VPS.
